## 电子书阅读器

一个从 0 到 1 用 AI 做桌面应用的实战案例：先做需求分析和产品设计，再定技术方案、写项目说 明，最后让 AI 按文档实现并测试。核心思路是「先跑通 MVP，再逐步迭代」。

## 一、需求分析

## 1. MVP 思路

想做一个东西，但不知道需要哪些功能时，可以跟 AI 聊一聊，让它给你建议。

MVP（Minimum Viable Product，最小可行产品）：第一版只做最核心、最必要的功能，先把产品跑 通，其他功能之后再加。

做一个电子书阅读器，打算先从MVP版本开始，你觉得这一版做哪些功能比较合适？

## 2. 生成 PRD 文档


帮我整理一份产品设计文档，不用太详细，把整体方向和主要功能梳理出来就可以了

## 3. 前端 Demo（可选）

正式开始项目之前，可以先让 AI 做一个前端 Demo（使用模拟数据），主要目的是让用户体验一下整 个界面的交互和操作流程。哪里感觉不对，就让 AI 修改这个 Demo，直到符合预期为止。

## 做 Demo 的好处：

- 提前验证产品设计：光靠文字其实很难想象，把页面先画出来之后，可能会发现之前没想到的问 题；如果设计不合理，可以继续修改 Demo，同步修改对应的 PRD 文档。

- 让后续实现更精确：Demo 可以非常直观地告诉 AI"我最终想要的产品大概就是这个样子"，这是 文字很难做到的。后面正式做项目时，把 PRD 文档和 Demo 一起给 AI，AI 既知道要做哪些功 能，也知道界面和交互该怎么还原，做出来的东西会更接近预期。

不过也不是所有项目都需要做 Demo。决定因素是后端实现成本：后端成本高，就做个 Demo；成本低 就不用做。像这个电子书阅读器后端简单，就不用做 Demo。

AI 制作 Demo 的指令：

帮我做一个demo，不用实现真实的后端功能，数据模拟一下就行，我主要想先看看整体界面和操作流程是否合 理。

## 二、技术设计

桌面应用一般是 Electron 或 Tauri，你可以跟 AI 探讨一下：

根据PRD.md文档，告诉我，用什么技术栈实现和这个产品比较合适，我们就是先探讨一下，我听说Electron 还可以，你怎么看

确定技术栈后，让 AI 生成一份 TECH_DESIGN.md 技术设计文档，把选型结论和实现方案记录下来。

## 三、编写 AGENTS.md

在项目根目录创建一个 AGENTS.md 文件，用 Markdown 写明：这个项目是什么、怎么跑起来、有哪 些硬性约定（技术栈、目录结构、代码风格等）。它是跨工具通用的项目说明，Codex、Copilot、 Cursor 等都能读取，具体写法可以参考《Cursor 安装使用》里的 Rules 章节。

## 四、实现

新开一个对话，把三份文档一起喂给 AI：

@AGENTS.md @PRD.md @TECH_DESIGN.md ，根据文档实现这个产品

在 AI 自测之后，也需要人工测试一下。如果发现问题，就发给 AI 让其修改。
